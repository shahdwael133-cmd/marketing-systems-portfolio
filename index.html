01 · how I work

My operating loop

Every system on this page went through the same 6 steps. The last one matters most: a product needs a reason to die, decided before it ships.

step 1

Problem

Name the user and the job they're stuck on.

Engineers want to inspect a CAD file without uploading it anywhere.
step 2

Hypothesis

Write what I expect to happen, and what would prove me wrong.

A free viewer pulls high-intent engineers into the quote flow.
step 3

Spec

Pick the trade-offs on paper before writing code.

Parse files client-side. Keep first load under 1 MB.
step 4

Ship

Smallest version that tests the hypothesis, behind real tests.

v1 on day one, v2 live 5 days later.
step 5

Instrument

Track the event that answers the question, not vanity numbers.

Quote clicks tagged "own file" vs "sample file".
step 6

Decide

Iterate, scale or kill, against criteria set in step 2.

No quote starts in 3 months means I stop investing.

A 3D CAD viewer that never uploads your file

About 5,400 people in the US search for a STEP file viewer every month. Almost all of them are engineers. That's my exact customer, already holding a part they need made.

The insight

Engineers are protective of their geometry. Asking them to upload a file to a vendor they don't know is friction before trust exists. So the tool had to work without the file ever leaving their machine.

This is called engineering as marketing. You build a free tool your customer already needs, and the tool does the acquisition for you.

The part nobody sees

Language models are great at narrative and unreliable at arithmetic. So I split the job: 2,765 lines of deterministic code own every number, and the AI only writes the paragraph around them. Same input, same output, every run.

This is called separation of concerns. Each part of a system does one job, so a failure in one can't corrupt another.

A week of content, produced while I sleep

One part-time person can't film, edit, design and caption a full week of multichannel content. So I built a team of agents that does it, and kept the one job that needs judgment: approval.

The failure that made it better

v1 ran on my laptop through Windows Task Scheduler. It failed 3 times unattended. Instead of patching it, I migrated the whole pipeline to cloud agents, then ran the same renders in both environments and diffed them pixel by pixel. Maximum difference: 1.7%.

This is called a parity test. Before you switch infrastructure, you prove the new system produces the same output as the old one.

case 4 / 5 · measurement
My role
PM and analyst
Users
Leadership, sales, a new SEO hire
Timeline
Designed 29 Oct, baseline 2 to 22 Nov, readout Jan 2027
Stack
GA4 Data API, tag management, Node stats scripts
Status
Baseline collected, test running

Replacing opinions with an experiment

A website rebuild was coming, and every decision was being argued on taste. Worse, nobody agreed on what a "qualified lead" even was, so nobody could say whether anything worked.

What I set up, in order

1. Clean instrumentation. Cut the event taxonomy to 3 conversion events (quote_click, form_submit, a call booking) so each is counted once, and extended data retention to 14 months.

2. A shared definition. An A/B/C fit grade on every inbound lead, so marketing and sales mean the same thing by "qualified".

3. A baseline before any change. 3 weeks of untouched data, then changes rolled out in a fixed window.

4. Power maths up front. I calculated the noise in our weekly numbers before the test, so I know how big a change has to be before it counts as real.

This is called statistical power. If your test can't detect the effect you care about, a "no difference" result means nothing.

Conversion events per session

secondary

Lead grade mix, time to first quote

guardrails

Engagement rate, bot traffic excluded

decision_rule

Ship changes that beat the noise floor, roll back the rest

07 · principles

How I build

end_to_end

A system runs from data in to result delivered. No manual step hiding in the middle.

fail_closed

When inputs are wrong, the system stops and tells me. It never guesses.

dry_run_first

Every automation passes a full test run and ships with a written runbook.

acceptance_criteria

Pass/fail rules are written before the build, then the output is scored against them.

ground_truth

Real data and verified facts only. No invented numbers, no synthetic people in content.

cost_ceiling

Free tiers first. Anything paid gets tested at the smallest scale before full volume.
